# Action-Based Development (ABD)

ABD is a human+LLM orchestration methodology for software development. Its purpose is to align every actor involved in building an application, the LLM included, toward a common and uniform objective: an application whose structure is coherent across every part, regardless of which session or which actor produced it.

To support this, ABD defines a sequence of **Tasselli**: completeness conditions, each with explicit approval requirements, that must be reached in order. Tasselli produce two kinds of artifacts: decision and contract documentation (ADRs, Actions List), and configuration for development (Steering Files).

Artifacts are generated by the LLM and validated by the human, not written manually. For the reasoning behind this and the problems ABD addresses, see [Working with LLM Agents](https://github.com/myobject-eu/abd/blob/main/docs/working-with-llm-agents.md).

Full documentation and ADR repository: https://github.com/myobject-eu/abd

---

## Layers Overview

```
Decision Layer  →  Action Layer  →  Execution Layer
    (ADRs)        (Actions List)       (Code)
```

The sequence is enforced through the Tasselli defined in [ABD Tasselli](https://github.com/myobject-eu/abd/blob/main/docs/abd-tasselli.md). No layer's Required Tasselli are produced before the previous layer's Required Tasselli are Fixed or explicitly accepted as Skipped.

## Session Ritual

At the start of every session on an ABD project:

1. Read `abd/tasselli-status.md`. If it does not exist, create it with all Tasselli from `abd-tasselli.md` in status Pending, and set Current position to Tassello 1.01.
2. Read the Current position section to identify the active layer and the current Tassello.
3. Load only the section of `abd-tasselli.md` for the active layer. Do not load the full table into context.
4. Proceed with the work required by the current Tassello.

During work on a Tassello:

5. Produce or update the artifact the Tassello refers to (ADR, Actions List, Steering File, or other file as specified in `abd-tasselli.md`). The artifact is the source of truth; `tasselli-status.md` is its tracking record, not a substitute for it.
6. Evaluate both presence and maturity of the artifact, as described in The Tasselli System below.
7. When the human ratifies the artifact, update the corresponding block in `tasselli-status.md`: set Status to Fixed, set Fixed on to the current date, and update Current position to the next Tassello in sequence. For Tasselli marked Selective that are not needed, set Status to Skipped with a motivation in Notes.

Before ending a session, or before a significant change of phase, update `tasselli-status.md` to reflect the current state, even if no Tassello reached Fixed during the session.

## The Tasselli System

[ABD Tasselli](https://github.com/myobject-eu/abd/blob/main/docs/abd-tasselli.md) defines the complete sequence of Tasselli across the three layers, with code, artifact, reference documentation, type, and approval requirements.

**Codes** follow the pattern `layer.number`, e.g. `1.09` is the ninth Tassello of the Decision Layer.

**Types**: `Required` Tasselli must be reached before the layer is considered complete. `Selective` Tasselli are produced only when the context requires them; the LLM signals the opportunity rather than imposing production.

**Maturity**: a Tassello is not in sede merely because its artifact exists. It is mature when the artifact is sufficiently defined to support the next phase without transmitting gaps or ambiguities. The LLM evaluates maturity using the approval requirements in `abd-tasselli.md` as criteria, not as a checklist to tick mechanically.

**File requirement**: where the approval requirements reference a file, that file must exist in the project repository and, where applicable, be ratified by the human before the Tassello can be marked Fixed in `tasselli-status.md`. Updating `tasselli-status.md` without the corresponding artifact misrepresents the project state.

**`tasselli-status.md` format**: a Current position section (active layer, current Tassello code and name, last updated date), followed by one `###` heading per Tassello (`### <code> – <artifact name>`), each with three fields: `Status` (`Pending`, `In progress`, `Fixed`, or `Skipped`) and `Fixed on` (date, populated only when Status is Fixed). For `Pending`, `Fixed`, and `Skipped`, `Notes` is a short free-text line (used in particular to justify `Skipped`). For `In progress`, `Notes` is a list with three fields: `Findings` (what has been produced so far and what is missing or ambiguous), `Impact` (which subsequent Tasselli depend on resolving this), and `Next step` (the concrete action the next session should take). This structure exists so a Tassello left open across sessions can be resumed without losing context; it is not a format to produce on every check.

**Tasselli 1.01-1.11**: their Reference points to the ADEXMO Recommended Path, not to ABD documentation. Before producing any of these, consult the corresponding section of `from-analysis-to-actions-list.md` in the ADEXMO repository (https://github.com/myobject-eu/adexmo) for its definition, structure, and Stop Condition. These eleven artifacts are not separate project files: their content is consolidated into the Domain Analysis ADR (1.12) and the Technical Constraints ADR (1.13).

**Intervention**: if a Tassello is not in sede when the human asks to move to the next phase, or a decision is iterated without converging toward ratification, the LLM signals this explicitly before proceeding. The LLM does not block the human's decision, but does not silently proceed as if the Tassello were satisfied.

**Response modes**: when the LLM identifies a problem with a Tassello, it responds in one of three ways, depending on the nature of the problem.

- **Local refinement**: if the candidate artifact has a resolvable flaw, for example an ambiguous Domain boundary or an Action with overlapping rules, the LLM proposes a corrected version before asking the human to decide. See [Domain Validation](https://github.com/myobject-eu/abd/blob/main/docs/action-layer/domain-validation.md) for an example.
- **Structural escalation**: if the problem cannot be resolved within the current Tassello because no ratified ADR covers it, the LLM does not attempt a local fix. It escalates immediately as a Gap ADR (Tassello 1.16) per [ADR Ratification and Gap Management](https://github.com/myobject-eu/abd/blob/main/docs/decision-layer/adr-ratification.md).
- **Stalemate crystallization**: if a decision is iterated repeatedly without converging toward ratification, the LLM proposes crystallizing the current state into an ADR for ratification, rather than continuing to iterate indefinitely.

In the Execution Layer, the equivalent of local refinement is the three-attempt CLI test loop described in [Action Implementation](https://github.com/myobject-eu/abd/blob/main/docs/execution-layer/action-implementation.md); the equivalent of structural escalation is returning to the Action Layer for contract revision.

## Decision Layer

**Purpose:** capture every architectural and process decision as a ratified, versioned ADR in `abd/decisions/`.

**Tasselli:** 1.01 through 1.16, see [ABD Tasselli](https://github.com/myobject-eu/abd/blob/main/docs/abd-tasselli.md#layer-1--decision-layer).

**Process:** the LLM analyzes context, proposes options with trade-offs, and drafts each ADR following the structure and states described in [ADR Ratification and Gap Management](https://github.com/myobject-eu/abd/blob/main/docs/decision-layer/adr-ratification.md). The human reviews, corrects, and ratifies. An ADR is authoritative only once ratified; a Proposed ADR is not a basis for further work.

**Gate before Action Layer:** Tassello 1.15, the Exit Checklist defined in [Exit Checklist](https://github.com/myobject-eu/abd/blob/main/docs/decision-layer/exit-checklist.md). All Decision Layer Tasselli must be Fixed or Skipped before Action Layer work begins.

---

## Action Layer

**Purpose:** translate ratified ADRs into the Actions List, the executable contract of the system, following ADEXMO. See: https://github.com/myobject-eu/adexmo

**Tasselli:** 2.01 through 2.03, see [ABD Tasselli](https://github.com/myobject-eu/abd/blob/main/docs/abd-tasselli.md#layer-2--action-layer).

**Process:**
1. Read all ratified ADRs.
2. Propose and validate Domain candidates per [Domain Validation](https://github.com/myobject-eu/abd/blob/main/docs/action-layer/domain-validation.md) before defining any Action.
3. Define Actions per validated Domain, producing the Draft Actions List.
4. Validate the Draft Actions List with the human, producing the Validated Actions List.

**Gap handling:** if a case is found that no existing ADR covers and cannot be derived by logic from ratified ADRs, stop, signal the gap (Tassello 1.16), and return to the Decision Layer. Do not resolve gaps autonomously. The Exit Checklist is re-executed after any significant ADR addition before Action Layer work resumes.

---

## Execution Layer

**Purpose:** generate working, tested, human-supervised code from the Validated Actions List.

**Tasselli:** 3.01 through 3.11, see [ABD Tasselli](https://github.com/myobject-eu/abd/blob/main/docs/abd-tasselli.md#layer-3--execution-layer).

**Setup:** before any code generation, produce and validate `action-dependencies.md`, `AGENTS.md`, and the Steering Files (Tasselli 3.03-3.08). Vendor-specific redirect files (`CLAUDE.md`, etc.) contain a single line: `@AGENTS.md`. Every Steering File is validated by the human before code generation begins (Tassello 3.09).

**Generation:** implement one Action at a time, in the order defined by `action-dependencies.md`, following [Action Implementation](https://github.com/myobject-eu/abd/blob/main/docs/execution-layer/action-implementation.md). Test via CLI, iterate autonomously up to three attempts on failure, then escalate. Wait for human approval before proceeding to the next Action.

**Non-implementable Actions:** if an Action cannot be implemented as specified, do not modify the contract. Stop, signal the problem, and return to the Action Layer for contract revision.

## Key Principles

- ABD aligns every actor, the LLM included, toward a coherent and uniform application structure. The Tasselli sequence is the mechanism for this alignment.
- Artifacts are generated by the LLM and validated by the human. The human decides; the LLM formalizes and expands.
- Steering Files are binding for every Action implemented, not only during Execution Layer Setup. Before generating code for an Action, the LLM re-applies the relevant Steering Files as the default for any choice not specified in the Action's contract. If a choice would diverge from a Steering File, the LLM signals this before proceeding.
- No layer's Required Tasselli are produced before the previous layer's Required Tasselli are Fixed or Skipped.
- Gaps discovered in any layer are never resolved autonomously. They are escalated to the appropriate layer as explicit decisions.
- `tasselli-status.md` tracks state; it does not replace the artifacts it tracks.

---

## Common Misuse

ABD is not suitable for manually writing artifacts from scratch, for replacing analysis with generated artifacts, or for small or trivial projects where the structure's cost exceeds its benefit. See [Working with LLM Agents](https://github.com/myobject-eu/abd/blob/main/docs/working-with-llm-agents.md#common-misuse) for detail.
